# Prevent Root Filesystem Exhaustion

## Diagnosis

- Azula's 98 GiB root filesystem also contains `/nix/store`; after manual cleanup the store is still 44 GiB and root usage is 60 GiB (65%).
- No active host currently enables automatic Nix garbage collection or store optimisation. Flake updates and rebuilds therefore accumulate store paths until `~/bin/nix-hygiene` is run manually.
- Azula retains five recent system generations and has no systemd-boot generation limit. `my-machine` uses GRUB; `azula` and `toph` use systemd-boot.
- `/var/log/journal` is 4 GiB, which matches systemd's default cap. Per the user's choice, leave it unchanged.
- `/var/lib/libvirt/images/GentleAI.snapshot1` consumes 11 GiB on root. It is absent from the active storage pools and both defined domains (`Jarvis` and `Insight`), and its backing image is missing. Treat it as a guarded one-time cleanup.

## Implementation

1. Add `modules/features/system-storage.nix` exporting `flake.nixosModules.systemStorage`.
   - Enable `nix.gc.automatic` on a weekly systemd calendar.
   - Set `nix.gc.options = "--delete-older-than 14d"` so old profile/system generations stop retaining obsolete closures indefinitely.
   - Enable `nix.optimise.automatic` weekly, scheduled after GC so dead paths are not optimised first.
   - Set shared `nix.settings.min-free` and `max-free` defaults to 5 GiB and 10 GiB. These make the Nix daemon attempt GC before a build consumes the final free space while remaining conservative for the VM and laptop.
   - Use `lib.mkMerge`/`lib.mkIf` to cap the enabled bootloader at 10 menu generations: `boot.loader.systemd-boot.configurationLimit` for systemd-boot hosts and `boot.loader.grub.configurationLimit` for GRUB hosts.
2. Import `self.nixosModules.systemStorage` from all active hosts:
   - `modules/hosts/azula/configuration.nix`
   - `modules/hosts/toph/configuration.nix`
   - `modules/hosts/my-machine/configuration.nix`
3. In `modules/hosts/azula/configuration.nix`, override the shared free-space defaults with 10 GiB `min-free` and 20 GiB `max-free`. Azula's known 98 GiB root and large NVIDIA closures justify the larger build safety margin.
4. Do not modify journald settings or `~/bin/nix-hygiene`; the declarative timers replace the need to rely on that script for routine cleanup, while the script remains available for manual recovery.

## One-Time Cleanup

1. Before deletion, re-list all libvirt domains, pools, volumes, and domain block devices; search libvirt domain/snapshot XML and open process descriptors for `/var/lib/libvirt/images/GentleAI.snapshot1`.
2. Confirm again that the file is unreferenced and that `qemu-img info --backing-chain` reports its missing `/var/lib/libvirt/images/GentleAI.qcow2` backing image.
3. Remove only `/var/lib/libvirt/images/GentleAI.snapshot1`, then verify the directory and root filesystem reclaimed approximately 11 GiB. Do not touch the similarly named VM volumes under the separately mounted `/home/fedex/VMs` pool.

## Verification

1. Stage the new module file before flake evaluation because Git flakes omit untracked files; leave the user's existing `flake.lock` update and unrelated `.atl/` state untouched.
2. Run `nix eval .#nixosModules --apply builtins.attrNames` and confirm `systemStorage` is exported.
3. Evaluate all three host configurations and confirm:
   - GC is automatic, weekly, and passes `--delete-older-than 14d`.
   - Optimisation is automatic and weekly.
   - `azula` has 10/20 GiB free-space thresholds; `toph` and `myMachine` have 5/10 GiB.
   - `azula`/`toph` systemd-boot limits and `myMachine` GRUB limit are 10.
4. Run `nix flake check`, then dry-build `.#nixosConfigurations.azula.config.system.build.toplevel`, `.#nixosConfigurations.toph.config.system.build.toplevel`, and `.#nixosConfigurations.myMachine.config.system.build.toplevel` to catch cross-host evaluation/build-plan regressions without activating them.
